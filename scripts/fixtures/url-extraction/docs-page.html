Query Caching

The cache stores the result of every resolved query under a key derived from its arguments. A second request with the same key is served from memory instead of hitting the network, which is what makes repeated navigation feel instant. Nothing is written to disk, so the cache is empty again on a full page load and warms up as the first few screens resolve.

Entries are held until either the entry limit is reached or the owning provider is torn down. Because the limit is counted in entries rather than bytes, a query that resolves to a very large payload occupies exactly as much of the budget as one that resolves to a single number.

Cache Keys

A cache key is a stable serialization of the query arguments. Two queries share a cache entry only when their keys are deeply equal, so argument order does not matter but argument values do. The serializer sorts object properties before hashing, which is what makes the comparison independent of the order the caller happened to write the arguments in.

Key Stability

Keys must not contain values that change on every render. Passing a freshly constructed object or a timestamp produces a new key each time and defeats the cache entirely. The symptom is a cache that grows without bound while its hit rate stays at zero, which is worth checking first whenever caching appears to do nothing at all.

Values that are stable by construction are safe to include. Route parameters, identifiers and enumerated filter values all serialize to the same key across renders and are the usual building blocks of a well behaved key.

Key Collisions

Two unrelated queries that serialize to the same key will read each other's data. Namespacing every key with the resource name avoids this without any additional bookkeeping, and it makes the cache contents readable when they are dumped during debugging.

Collisions are silent. There is no runtime warning when two callers converge on one key, so the convention has to be enforced by review or by a helper that builds keys from a resource name and an argument object rather than by hand.

Invalidation

Invalidation marks entries as stale rather than deleting them. Stale entries are still served while a background refetch runs, so the interface never falls back to a loading state it has already passed through. The refetch replaces the entry when it resolves, and subscribers re-render once at that point rather than twice.

Deletion is available as a separate operation for the cases where serving stale data would be wrong, such as after a sign out. Prefer invalidation everywhere else, because deletion reintroduces exactly the loading states the cache exists to remove.

Invalidation is asynchronous. Awaiting the invalidation call does not guarantee that dependent queries have finished refetching.
